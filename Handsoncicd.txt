Part 1 – What is CI/CD?
    Let's first understand the problem.

    Imagine a company has the following Data Engineering code:
        ETL Scripts
        SQL Files
        Airflow DAGs
        Spark Jobs
        Python Transformations
        Configuration Files

    For example:

        data-engineering-project/
        │
        ├── etl/
        │   ├── extract.py
        │   └── transform.py
        │
        ├── sql/
        │   ├── employees.sql
        │   └── sales.sql
        │
        ├── dags/
        │   └── daily_pipeline.py
        │
        ├── spark/
        │   └── sales_job.py
        │
        └── tests/
            └── test_etl.py

    Suppose a developer changes an ETL script directly on the production server.

They make a mistake.

    For example:
        print("Processing customer data")

    becomes:
        print("Processing customer data"

    There is a missing ).

    The production pipeline breaks

Problems with the old approach

    Without CI/CD:

        Developer writes code
                ↓
        Copy code to server
                ↓
        Run manually
                ↓
        Something breaks
                ↓
        Try to fix manually

    Problems:

        No proper version history
        Difficult rollback
        Manual deployment
        No automated testing
        Human errors
        Team members can overwrite each other's work
        Production can break
        Difficult to identify who changed what

Part 2 – What is CI?

    CI means:
        Continuous Integration

    The basic idea is:
        Whenever developers make changes to code, the system automatically 
        checks the code.

    For example:

        Developer changes code
                ↓
        Push code to GitHub
                ↓
        CI pipeline starts
                ↓
        Install dependencies
                ↓
        Run tests
                ↓
        Validate code
                ↓
        PASS / FAIL

    For Data Engineering, CI can test:

        Python ETL code
        SQL
        Airflow DAGs
        PySpark code
        Data transformations
        Configuration files


Part 3 – What is CD?

    CD can mean:
        Continuous Delivery

    or
        Continuous Deployment

    The important idea is that after the code passes validation, it can be prepared or deployed to another environment.

    For example:

        Developer
            ↓
        Git
            ↓
        CI
            ↓
        Tests
            ↓
        Validation
            ↓
        Deployment
            ↓
        Airflow / Spark / Data Platform

Part 5 – Why Data Engineers Need Git
    Git is a version control system.
    It tracks changes to your files.

    Data Engineers commonly use Git for:
        Python ETL scripts
        SQL files
        Airflow DAGs
        PySpark jobs
        Configuration files
        Data quality tests
        Deployment scripts

    Git provides:
        1. Version history
        You can see what changed.

        2. Collaboration
        Multiple developers can work on the same project.

        3. Rollback
        You can return to an earlier version.

        4. Branching
        Developers can work on separate features.

Now create python-ci.yml

For your local CI simulation, use:

name: Python CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Run tests
        run: |
          pytest        



What this means
    Your CI process will eventually do:
        Developer pushes code
                ↓
        GitHub Actions starts
                ↓
        Download repository
                ↓
        Install Python
                ↓
        Install requirements
                ↓
        Run pytest
                ↓
        PASS / FAIL 

It is a GitHub Actions workflow definition.

    You are doing:

    Step 1
        Local Python
            ↓
        pytest
            ↓
        Verify test works

    Step 2
        GitHub
            ↓
        Push repository
            ↓
        GitHub Actions reads
        .github/workflows/python-ci.yml
            ↓
        Runs the same test automatically
