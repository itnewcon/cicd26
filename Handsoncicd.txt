Part 1 – What is CI/CD?
    Let's first understand the problem.

    Imagine a company has the following Data Engineering code:
        ETL Scripts
        SQL Files
        Airflow DAGs
        Spark Jobs
        Python Transformations
        Configuration Files

    For example:

        data-engineering-project/
        │
        ├── etl/
        │   ├── extract.py
        │   └── transform.py
        │
        ├── sql/
        │   ├── employees.sql
        │   └── sales.sql
        │
        ├── dags/
        │   └── daily_pipeline.py
        │
        ├── spark/
        │   └── sales_job.py
        │
        └── tests/
            └── test_etl.py

    Suppose a developer changes an ETL script directly on the production server.

They make a mistake.

    For example:
        print("Processing customer data")

    becomes:
        print("Processing customer data"

    There is a missing ).

    The production pipeline breaks

Problems with the old approach

    Without CI/CD:

        Developer writes code
                ↓
        Copy code to server
                ↓
        Run manually
                ↓
        Something breaks
                ↓
        Try to fix manually

    Problems:

        No proper version history
        Difficult rollback
        Manual deployment
        No automated testing
        Human errors
        Team members can overwrite each other's work
        Production can break
        Difficult to identify who changed what

Part 2 – What is CI?

    CI means:
        Continuous Integration

    The basic idea is:
        Whenever developers make changes to code, the system automatically 
        checks the code.

    For example:

        Developer changes code
                ↓
        Push code to GitHub
                ↓
        CI pipeline starts
                ↓
        Install dependencies
                ↓
        Run tests
                ↓
        Validate code
                ↓
        PASS / FAIL

    For Data Engineering, CI can test:

        Python ETL code
        SQL
        Airflow DAGs
        PySpark code
        Data transformations
        Configuration files


Part 3 – What is CD?

    CD can mean:
        Continuous Delivery

    or
        Continuous Deployment

    The important idea is that after the code passes validation, it can be prepared or deployed to another environment.

    For example:

        Developer
            ↓
        Git
            ↓
        CI
            ↓
        Tests
            ↓
        Validation
            ↓
        Deployment
            ↓
        Airflow / Spark / Data Platform

Part 5 – Why Data Engineers Need Git
    Git is a version control system.
    It tracks changes to your files.

    Data Engineers commonly use Git for:
        Python ETL scripts
        SQL files
        Airflow DAGs
        PySpark jobs
        Configuration files
        Data quality tests
        Deployment scripts

    Git provides:
        1. Version history
        You can see what changed.

        2. Collaboration
        Multiple developers can work on the same project.

        3. Rollback
        You can return to an earlier version.

        4. Branching
        Developers can work on separate features.

Part 8 – Verify Git Installation
    Open VS Code.

    Open:
        Terminal → New Terminal

    You should see a terminal at the bottom.

    Type:
        > git --version

    Press Enter.

    You should get something similar to:
        git version 2.x.x

    The exact version may be different.
    If you see a Git version, Git is installed correctly.

Part 9 – Configure Git
    Before creating commits, configure your name and email.

    In VS Code terminal, type:
        > git config --global user.name "Your Name"

    Example:
        > git config --global user.name "Yuvan"

    Now configure your email:
        > git config --global user.email "your-email@example.com"

    Use the email associated with your GitHub account.

    Check your configuration:
        > git config --global user.name

    Then:
        > git config --global user.email

    You should see your configured values.

Part 11 – Create First ETL File
    In VS Code Explorer:
        Right-click session37.

    Select:
        New File

    Name it:
        etl.py

    Add:
        def extract_data():
            print("Extracting data")


        def transform_data():
            print("Transforming data")


        def load_data():
            print("Loading data")

            extract_data()
            transform_data()
            load_data()

    Save:
        Ctrl + S

Part 13 – Initialize Git
    In the VS Code terminal:
        > git init

    You should see something similar to:

    Initialized empty Git repository

    This creates a hidden:
        .git

    folder.

    You normally don't need to modify this folder manually.

Part 14 – Check Git Status
    Run:
        > git status

    You should see something similar to:

    Untracked files:
        etl.py
    What does "untracked" mean?

    Git sees the file, but Git is not currently tracking it.

Part 15 – Add the File
    Run:
        > git add etl.py

    Now run:
        > git status

    You should see:

        Changes to be committed:
            new file: etl.py

    This means Git has placed the file in the staging area.


Part 16 – Commit the File
    Run:
        > git commit -m "Initial ETL code"

    You should see something similar to:

    1 file changed

    Your first Git commit is complete.

    Understand Git's Three Important Areas

    This is extremely important.

        Working Directory
            ↓
            git add
            ↓
        Staging Area
            ↓
        git commit
            ↓
        Git Repository

        For example:

        Create etl.py
            ↓
        git add etl.py
            ↓
        git commit -m "Initial ETL code"

Part 19 – What Does git add . Mean?
    Instead of:
        > git add etl.py

    you can use:
        git add .

    The . means:
        Add changes from the current directory.

    Typical workflow:
        > git add .
        > git commit -m "Updated ETL code"

Part 26 – Git Workflow

    The basic Git workflow is:

    Create / Modify file
            ↓
    git status
            ↓
    git add .
            ↓
    git commit -m "message"
            ↓
    git push

    Remember this workflow.

Part 27 – Understanding Branches

    A branch is a separate working area for your code.

    Suppose production currently has:

    main

    You want to create a new ETL transformation.

    Instead of modifying production code directly:

    main

    create:

    feature-transform

    Then work there.

Part 28 – Create Feature Branch

    Run:

    git checkout -b feature-transform

    Check:

    git branch

    You should see:

    * feature-transform
    main

    The * tells you which branch you are currently using.
